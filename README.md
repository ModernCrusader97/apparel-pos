# apparel-pos

의류 매장용 POS. **파이썬만 있으면 됩니다 — 설치할 패키지가 없습니다.**

표준 라이브러리만으로 서버·DB·HTTP·백업·프린터까지 다 합니다. 가상환경도, `pip install`도,
빌드 단계도 없습니다. 파일 두 개를 매장 PC에 복사하고 `python pos.py` 하면 끝입니다.

```bash
python pos.py --seed
```

→ http://localhost:8000 . 첫 실행 때 콘솔에 찍히는 **점주 계정 `admin`** 으로 로그인합니다.
비밀번호는 `POS_ADMIN_PW` 환경변수로 정하고, 안 주면 `admin1234` 입니다 (로그인 후 바로 바꾸세요).

매장의 다른 단말(태블릿·다른 PC)에서도 쓰려면 서버 역할 PC에서:

```bash
python pos.py --host 0.0.0.0 --port 8000
```

다른 기기에서 `http://서버PC의IP:8000` 으로 접속합니다.

## 의류 매장에 맞춘 것들

### 색상 × 사이즈 SKU

같은 옷의 색상·사이즈 하나하나가 **별개의 SKU** 입니다. 재고·판매·바코드가 전부 그 단위로 돕니다.

```
품번 TS-2601 / 베이직 반팔티 / 블랙,화이트,네이비 / S,M,L,XL  →  12개 SKU 일괄 생성
```

재고 탭의 기본 화면이 **품번별 색상×사이즈 매트릭스**입니다. 숫자를 누르면 그 SKU 의 입출고 창이
열립니다. 사이즈 정렬은 XS·S·M·L·XL·2XL·3XL·FREE 순이고, 숫자 사이즈(26/28/30/32)는 숫자 순입니다.

### 제조사 택 바코드 등록

일괄등록이 만드는 `품번-색상-사이즈` 바코드는 **실제 옷에 없습니다.** 품번 머리줄의
`택 바코드 등록` 을 누르면 그 품번 SKU 를 차례로 띄우고, 옷의 택을 스캔하면 저장하고 다음으로
넘어갑니다. 다른 상품이 쓰는 바코드면 **어느 상품인지 이름을 알려주고** 막습니다.

### 품절 응대

품절된 옷의 택을 스캔하면 장바구니에 담지 않고, **같은 품번의 다른 색상·사이즈 재고**를 같이
띄웁니다. 손님이 "다른 사이즈 있어요?" 물을 때 재고 탭으로 건너가지 않아도 됩니다.

### 재고 실사

범위를 정하고 스캔하며 세면 누적되고, 장부와의 차이를 보여준 뒤 한 번에 반영합니다.
**반영 시점에 장부를 다시 읽어** 비교하므로, 세는 동안 일어난 판매가 실사 오차로 둔갑하지
않습니다. 스캔하지 않은 SKU 는 '미확인'으로 두고 건드리지 않습니다 — 부분 실사가 더 흔합니다.

### 발주 제안

판매속도로 "뭘 몇 장 더 시켜야 하는지" 뽑습니다.

```
일평균 판매 = 기간 판매수량 ÷ 실제 판매 가능일수
목표 재고   = 일평균 × (입고 소요일 + 커버 일수)
권장 발주   = max(목표 재고, 안전재고) − 현재고
```

**'실제 판매 가능일수'로 나누는 게 핵심입니다.** 2주 전 들어온 신상을 30일로 나누면 판매속도가
절반으로 깎여 잘 나가는 신상이 재발주에서 빠집니다. 취급 시작일부터만 셉니다.

상태는 **품절**(팔리는데 재고 0) · **보충** · **안팔림**(2주 넘게 0장, 발주 금지) · **충분** 네 가지이고,
발주서 CSV 를 거래처에 그대로 보낼 수 있습니다.

### 시즌 할인

품번 단위 할인율에 기간을 둡니다.

```
판매가 = 정가 × (100 − 할인율) ÷ 100   (원 단위 내림, 서버가 계산)
결제   = 소계 − 건별 수기할인 − 포인트사용
적립   = 결제금액 × 적립률
```

장바구니·영수증에 정가와 할인가가 같이 보이고, 정산은 **시즌할인과 수기할인을 따로** 보여줍니다.
합치면 "정가로는 얼마였나"가 사라져 시즌오프 효과를 영영 못 봅니다.
`sale_items.price` 에는 그때 실제로 판 금액이 들어가므로, 나중에 할인율을 바꿔도
**과거 판매 금액은 흔들리지 않습니다.**

## 직원 권한과 감사 로그

| | 직원 | 매니저 | 점주 |
|---|---|---|---|
| 판매, 입고, 고객등록, 재고 조회 | O | O | O |
| 상품 등록·가격변경·택 바코드, 폐기·실사조정, 재고 실사, 발주, 시즌 할인 | | O | O |
| **판매취소**, **포인트 수기조정**, 정산·증빙, **일일 마감** | | O | O |
| 직원 계정, 감사 로그, 매장 설정, 백업 | | | O |

비밀번호는 `hashlib.scrypt` 로 해시해 저장합니다(평문 저장 안 함). 같은 아이디로 연속 실패가
5회를 넘으면 300초 잠깁니다 — 잠금 시간을 짧게 둔 건 영업 중에 직원을 오래 묶으면 그게 더 큰
사고이기 때문입니다.

돈·재고가 움직이는 민감 작업(**판매취소, 포인트조정, 재고폐기·실사, 가격변경, 바코드변경,
할인설정, 일일마감, 계정변경, 설정변경, 백업**)은 **누가 언제 무엇을** 했는지 감사 로그에 남고
지울 수 없습니다. 횡령·실수 추적용입니다.

## 일일 마감 (시재 정산)

```
예상 현금 = 개시 시재금 + 그날 들어온 현금 − 그날 나간 현금(환불)
```

- **들어온 현금** = 그날 *판매된* 현금 건 전부. 나중에 취소되더라도 그날 서랍엔 들어왔습니다.
- **나간 현금** = 그날 *취소된* 현금 건 전부. 판매일이 언제든 환불은 오늘 서랍에서 나갑니다.
- 당일 팔고 당일 취소하면 양쪽에 잡혀 저절로 상쇄되고, **어제 판 걸 오늘 환불하면 오늘 서랍에서만** 빠집니다.
- 개시 시재금은 전날 마감 때 센 금액을 이어받습니다.
- 매니저 이상이 로그인하면 **마감 안 된 지난 날짜**를 배너로 알립니다(최근 7일, 휴무일 제외).

## 카드단말(VAN)·현금영수증·세금계산서

카드 승인은 VAN사 계약 + 매장 PC 에 설치되는 결제모듈이 있어야 합니다.
이 프로그램은 **그 모듈을 호출하는 쪽**입니다.

```bash
POS_VAN_URL=http://127.0.0.1:9900/pay python pos.py
```

- 설정하면 결제 시 자동 승인, 판매취소 시 자동 승인취소, 현금영수증도 단말 경유 발급.
- 미설정이면 승인번호를 수기로 입력하는 모드로 동작합니다.
- VAN사마다 전문 규격이 다릅니다. 계약 후 받는 연동규격서대로 [`pos.py`](pos.py) 의
  **`van()` 함수 하나**만 고치면 됩니다. 기대 응답:
  `{"ok": true, "approval_no": "...", "card_name": "...", "message": ""}`

**카드 승인이 난 뒤 DB 기록이 실패하면 승인을 자동으로 취소합니다.** 돈만 빠져나가는 상황을
막기 위한 것입니다.

**현금영수증**은 국세청 직접 연동이 불가해 실무상 VAN사가 같이 처리합니다. 미연동이면 '대기'로
남겨 증빙 탭에서 승인번호를 수기로 채웁니다. **세금계산서**는 발행 자체가 홈택스·팝빌 몫이라,
사업자 고객의 월별 공급가액·세액을 집계해 **발행용 CSV** 로 내보내는 데까지 합니다.

## 영수증 프린터 (선택)

감열 프린터가 **네트워크(LAN)** 모델이면 서버가 직접 출력합니다.

```bash
POS_PRINTER=192.168.0.50:9100 python pos.py
```

- 결제하면 자동 출력되고, 영수증 창의 `프린터로 출력` 으로 재출력합니다.
- **미설정이면 브라우저 인쇄**를 씁니다. 동작이 바뀌지 않습니다.
- **USB 프린터는 안 됩니다.** 브라우저도 서버도 USB 장치에 직접 말할 수 없습니다.
- 출력이 실패해도 판매는 그대로이고, 실패는 감사 로그에 남습니다.

기종마다 코드페이지와 용지 폭이 달라 **실물로 맞춰야 합니다**:

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `POS_PRINTER_CP` | `cp949` | 한글 코드페이지. 글자가 깨지면 `euc-kr` 등으로 |
| `POS_PRINTER_WIDTH` | `42` | 한 줄 글자 수. 80mm=42, 58mm=32 |
| `POS_PRINTER_TIMEOUT` | `5` | 연결 대기 초 |

프린터 없이 출력 결과를 보려면 [`tools/fakeprinter.py`](tools/fakeprinter.py) 를 띄우고
`POS_PRINTER=127.0.0.1:9100` 으로 실행하세요. 받은 내용이 `printed.txt` 에 쌓입니다.

## 백업

```
backup/pos-20261013.db
```

**하루 1회** 자동 백업 + 마감할 때마다 1회. 기본 **14일 보관**, 오래된 건 자동 삭제.
파일 복사가 아니라 **SQLite 온라인 백업**을 쓰므로 영업 중에 돌려도 깨지지 않습니다.

백업 직후 그 파일을 **열어서** `PRAGMA quick_check` 와 판매 건수 일치를 확인합니다.
검증에 실패하면 그 파일을 지우고 보관 정리를 돌리지 않습니다 — 쓸모없는 백업이 보관 한도를
먹고 멀쩡한 이전 백업을 밀어내면, 정작 복구할 때 쓸 게 없습니다.

> **백업 폴더가 그 PC 안에만 있으면 PC 가 고장날 때 같이 날아갑니다.**
> `POS_BACKUP_DIR` 을 USB 나 클라우드 동기화 폴더로 잡아두세요.

복구는 백업 파일을 `pos.db` 자리에 덮어쓰고 재시작하면 끝입니다.

## 태블릿 / 데스크톱 / 폰

버튼 크기는 화면 크기가 아니라 **입력 장치**로 정합니다(`@media (pointer: coarse)`).
태블릿·터치 모니터에서는 모든 조작 요소가 자동으로 **48px 이상**이 되고, 마우스 데스크톱은
조밀한 밀도를 유지합니다. 설정이 필요 없습니다.

자동 감지가 안 맞는 기기를 위해 **설정 → 화면**에서 `자동 / 항상 크게 / 항상 작게` 를 고를 수
있고, 이 값은 **그 기기에만** 저장됩니다. 계산대 PC 는 작게, 매장 태블릿은 크게 쓸 수 있습니다.

폰(560px 미만)에서도 레이아웃이 깨지지 않습니다. 다만 한 화면에 들어오는 상품 수가 적어
**주 계산대로는 태블릿이나 데스크톱**을 권합니다. 폰은 외부에서 매출·재고 확인하는 용도입니다.

## 설계에서 지킨 것

- **가격은 항상 서버가 정합니다.** 브라우저가 보낸 금액은 무시합니다. 시즌 할인율도 서버가 적용합니다.
- **재고 차감 + 포인트 적립/사용 + 판매 기록은 하나의 트랜잭션입니다.** 중간에 실패하면 전부 취소됩니다.
- **네트워크 호출(카드 승인·프린터)은 트랜잭션 밖에서** 합니다. DB 락을 수십 초 잡지 않도록.
- **재고를 바꾸는 길은 `_apply_stock()` 하나입니다.** 입출고 이력과 감사 로그가 갈라지면
  "재고가 왜 이렇게 됐나"를 추적할 수 없습니다.
- **재고·포인트는 음수가 될 수 없습니다.**
- **포인트로 결제한 금액은 적립 대상에서 제외합니다** (포인트 무한증식 방지).
- **같은 결제 요청이 두 번 와도 판매는 한 건입니다.** 요청 키 확인이 카드 승인보다 **먼저**라,
  통신이 끊겨 다시 눌러도 카드가 두 번 승인되지 않습니다.
- 판매 취소 시 재고·포인트·카드승인이 되돌려집니다. 적립 포인트를 이미 써버린 고객은 자동 취소가
  막히고 수기조정을 요구합니다.
- **취소된 판매의 영수증에는 취소 표시가 인쇄물에도 남습니다.** 배경색이 아니라 테두리로 표시한
  이유는, 브라우저가 기본적으로 배경을 인쇄하지 않아 색으로만 하면 종이에서 사라지기 때문입니다.
- 상품 삭제는 숨김 처리이며 과거 판매 이력은 보존됩니다.
- 사업자등록번호는 국세청 체크섬으로 검증합니다.
- **날짜는 현지 시각 기준입니다.** `toISOString()` 은 UTC 라서 한국에서는 자정~오전 9시 동안
  하루 전 날짜를 줍니다 — 그대로 쓰면 아침마다 정산이 어제로 잡히고 마감이 어제 날짜로 저장됩니다.

`smoke.py` 는 서버를 띄우고 가짜 VAN 단말을 붙여 로그인·권한차단·카드승인/거절/취소·현금영수증·
세금계산서·발주·마감·백업·재시도 중복 방지·감사로그·로그아웃을 HTTP 로 확인합니다.

둘 다 외부 패키지 없이 돕니다.

---

## 구조

```
pos.py          서버 + DB + 비즈니스 로직 (표준 라이브러리만)
index.html      화면 전체 (빌드 단계 없음, 외부 스크립트 없음)
test_pos.py     로직 자가검증
smoke.py        HTTP 전 구간 + 가짜 VAN 단말
tools/          개발용 보조 (가짜 영수증 프린터)
BACKLOG.md      개선 항목과 그 결정 근거
```

데이터는 `pos.db` (SQLite) 한 파일입니다. 스키마가 바뀌어도 기존 DB 는 그대로 올라옵니다
(`MIGRATIONS` 가 없는 컬럼만 추가).
